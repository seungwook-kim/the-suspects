# 속도 개선 후보 찾기 (2026-10-15)

5단계 뒤 사용자 요청("속도를 올릴 수 있는 방법을 더 찾아봐, 로직으로 안 되면 라이브러리 교체도")으로
남은 시간이 어디서 나오는지 재고, 효과가 확실한 것만 바꿨다. 모델을 부르지 않는 측정부터 했다.

## 1. 서버 자체 처리 시간 — 바꿀 것 없음
가짜 LLM, 파일 DB, 행동 하나의 서버 시간(모델 시간 제외):

| 행동 | 시간 |
|:--|--:|
| 조사 | 5ms |
| 묻기 | 10~13ms |
| 화면 상태 조회 | 3ms |

LangGraph·저장·검색을 합쳐도 행동당 0.01초대다. 그래프 라이브러리나 저장소를 바꿀 이유가 없다.

## 2. 모델 연결 라이브러리 — 바꿀 것 없음
같은 가짜 서버(네트워크 없음)에 실시간 요청 30번:

| 경로 | 첫 조각 | 끝까지 |
|:--|--:|--:|
| langchain(ChatOpenAI) | 1.0ms | 2.0ms |
| httpx 직접 | 0.1ms | 0.1ms |

라이브러리가 더하는 시간은 호출당 1~2ms다. 모델 응답(수 초)에 비하면 없는 셈이라 교체 이득이 없다.

## 3. 질문 분류(시맨틱 라우터) — 가장 큰 남은 원인
검증용 문장 95개를 새로 만들었다(`evals/router_examples/validation.yaml`, PRD §17.3. 실제 플레이에서 LLM 라우터로 간 3문장 포함).

| 지표 | 값 | PRD 목표(§17.1) |
|:--|--:|:--|
| LLM 라우터로 넘어간 비율 | 42% (40/95) | 15% 이하 |
| 바로 분류한 문장의 정확도 | 91% (50/55) | 90% 이상 |

- 직접 쓴 질문 10개 중 4개꼴로 분류 모델 호출이 더 붙는다(개발 연결 약 4초, 그중 2~3초는 프로그램 시동).
- 기준값만 바꾸면 LLM 비율을 15% 아래로 내릴 수 있지만 정확도가 84%로 떨어진다(기준 0.25, 차이 0.01).
  n-gram 방식으로는 두 목표를 같이 맞출 수 없다.

### 버그: "꺼져 있던"이 욕설로 분류됨 (고침)
"백업이 꺼져 있던 거 알고 있었어요?"가 욕설 규칙("꺼져" 낱말 포함)에 걸려 부적절한 말로 처리됐다.
인물이 "말씀이 너무 심하시네요"라고 하고 평판·신뢰도가 깎인다. 명령으로 쓰인 경우(문장 끝, "꺼져라", "꺼지라고")만 잡게 고쳤다.

### 라이브러리 교체 시험: 다국어 문장 임베딩 — 더 나쁨
같은 규칙(예시와의 최대 유사도)에 n-gram 대신 진짜 임베딩을 넣어 봤다(저장소 의존성은 바꾸지 않고 임시 환경에서).

| 임베딩 | 크기 | 문장당 | LLM 비율 / 정확도 (가장 나은 조합) |
|:--|--:|--:|:--|
| n-gram(지금) | 없음 | 1ms 미만 | 42% / 93% · 22% / 85% |
| paraphrase-multilingual-MiniLM-L12-v2 | 0.22GB | 2.9ms | 77% / 91% · 25% / 70% |

한국어 질문의 의도 차이(수사·잡담·블러핑)를 n-gram보다도 못 잡았다. 더 큰 다국어 모델(embeddinggemma-300m 1.24GB,
Qwen3-Embedding-0.6B 양자화 1.12GB, potion-multilingual 0.5GB)은 내려받기가 커서 시험하지 않았다(결정 필요).

### 분류 모델을 더 빠른 모델로 — 이득 없음
실제로 LLM 라우터로 간 3문장을 같은 개발 연결로: 지금 모델 3.6~4.0초, 더 작은 모델 4.0~5.2초.
작은 모델이 기본으로 생각을 더 해서 출력이 2~4배 길었다(151 → 337~609토큰).

### 바꾼 것: 애매한 질문은 분류와 인물 답을 동시에 (PRD §14.1 병렬로 하기, D-62)
- 시맨틱 분류가 애매해 LLM 라우터를 부를 때, 수사 질문이라고 보고 검색 + 인물 답을 동시에 시작한다.
- 답의 이벤트는 붙잡아 두었다가, 라우터가 수사 질문(또는 증거 제시·블러핑 시도)으로 판정하면 이어서 내보낸다.
  다른 판정이거나 어려운 질문용 역할로 바뀌면 취소한다(실시간 경로라 생성도 멈춤).
- 판정 규칙은 그대로다. 기다리는 시간만 "라우터 + 답"에서 "둘 중 긴 쪽"이 된다.

```
uv run python -m server.llm.latency --stream-check 3 --question "집에 있었다는 증거는요?"
```

| 실제로 LLM 라우터로 간 질문 | 첫 대사 p50 | 행동 끝 p50 |
|:--|--:|--:|
| 전(라우터 → 답, 다 만든 뒤 보여 줌) | 7.6초 | 7.6초 |
| 후(동시에 + 첫 문장부터) | 3.5초 | 3.8초 |

## 4. 화면 글자 찍기 — 바꿈
한 글자 30ms로 고정이라, 100자 대사는 다 받아 놓고도 3초 동안 찍혔다(브라우저 측정: 45자에 1.3초).
밀린 글자가 40자를 넘으면 한 번에 여러 글자씩 찍어 1.2초 안에 따라잡게 했다. 짧은 대사는 지금처럼 한 글자씩.

## 5. 사건 만들기(자유 주제) — 제안만
실제 기록 2번: 86초, 100초. 차례로 도는 앞 세 단계가 대부분이다.

| 단계 | 시간 | 출력 |
|:--|--:|--:|
| 세계관 | 13~15초 | 1.3~1.5천 토큰 |
| 인물 | 25~37초 | 3.0~4.2천 토큰 |
| 사건 설계 | 26~29초 | 3.4~3.9천 토큰 |
| 기억(인물별 동시)·문서 | 13~21초 | 이미 동시 |

인물 단계를 "공통 뼈대(관계·범인 동기) → 인물별 세부를 동시에"로 나누면 15~20초 줄 것으로 본다.
인물끼리의 관계와 말투 겹침을 한 번에 맞추는 구조라 품질 위험이 있어 바꾸지 않았다(결정 필요).

## 아직 남은 큰 후보 (결정 필요)
1. 심문 중에는 LLM 라우터를 없애고, 인물 답 출력에 의도(수사·잡담·메타)를 함께 쓰게 하기.
   - 애매한 질문(약 40%)의 분류 호출 자체가 사라진다(핫 패스 LLM 1회).
   - PRD §7.1 라우터 설계를 바꾸는 일이다.
2. 더 큰 다국어 임베딩 모델 시험(0.5~1.2GB 내려받기). 분류와 기억 검색(지금 해시 임베딩)을 함께 개선할 수 있다.
3. 사건 만들기 인물 단계 나누기(위 5번).
