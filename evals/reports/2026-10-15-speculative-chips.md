# 추천 질문 답 미리 만들기 (2026-10-15)

응답 속도 개선 2단계. 기준선은 [2026-10-14 응답 지연 기준선](2026-10-14-response-latency.md).

## 목적
설정(`speed.speculative_chips: true`)과 PRD §14.1에는 있었지만 서버에 연결되지 않았던 "추측 생성"을 잇고 효과를 잰다.
같은 단계에서 "검색 미리 하기"(`prefetch_retrieval_on_enter`)를 할지 판단한다.

## 만든 것
- 화면이 심문을 시작할 때와 행동이 끝날 때마다 `POST /api/games/{id}/prepare {npc_id}`로 심문 중인 인물을 알린다.
- 서버는 그 인물의 질문 칩(최대 `speculative_chip_count`개) 답을 백그라운드로 만든다(`server/game/speculative.py`).
  - 실제 턴과 같은 노드(검색 → 인물 답 → 게임 마스터 검사)를 쓰고, 게임 상태는 복사본만 쓴다.
  - 수첩·기억·증거 같은 뒤처리는 칩을 실제로 누를 때 한다.
- 칩을 누르면 같은 상태일 때만 미리 만든 답을 쓴다. 아직 만드는 중이면 끝날 때까지 기다린다.
- 다른 행동을 하면 남은 준비분은 버리고, 준비 1번마다 (미리 만든 수, 쓴 수)를 판의 적중률 기록으로 옮긴다.
- 호출 기록에서 미리 만든 호출은 node 끝에 `:speculative`를 붙이고, 꺼내 쓴 답은 model `prepared`로 남긴다.
  지연 측정 도구가 플레이어가 실제로 기다린 시간만 질문 단위로 센다.

## 다시 돌리는 법
```
uv run python -m server.llm.latency --speculative 2          # A·B·C 방식을 2번씩 (진짜 모델 사용량이 든다)
uv run python -m server.llm.latency --speculative 2 --read 5  # 읽는 시간을 5초로
```
- 임시 폴더에 새 판을 만들고 그림은 끈다(사용자 게임 기록·그림 사용량에 영향 없음).
- 매번 새 판의 같은 첫 질문 칩(기본 사건, 황지호 "어젯밤 사건 시각쯤 어디 계셨어요?")을 누른다.
- 기다린 시간 = `act()` 전체(서버가 이벤트를 다 낼 때까지). 화면 연출 시간은 빠져 있다.

## 결과
환경: 개발 PC, 개발용 프로필 `dev`(명령줄 도구, 같은 모델), 2026-10-15 새벽.

| 방식 | 1차(임시 스크립트) | 2차(측정 도구) |
|:--|:--|:--|
| A. 미리 만들기 없음 | 4.7, 4.4초 | p50 4.7초, 최대 4.8초 |
| B. 미리 만들기 시작 직후 누름 | 4.5, 4.5초 | p50 4.2초, 최대 4.3초 |
| C. 8초 읽고 누름 | 0.0, 0.0초 | p50 0.0초, 최대 0.0초 |

- 2차 호출 기록: 미리 만든 호출 6개 p50 4.3초(플레이어는 기다리지 않음). 미리 만든 답 8개 중 4개 사용.
- 출력 토큰은 미리 만든 답과 평소 답이 같은 수준(182 / 184). 답의 내용과 말투도 같은 경로라 같은 수준이다.

## 해석
- 플레이어가 앞 답을 읽는 동안(보통 수 초) 다음 칩 답이 끝나면, 칩 질문의 기다림은 0초가 된다.
- 심문을 열자마자 바로 칩을 누르면(B) 이득이 거의 없다. 만드는 중인 답을 기다리기 때문이다(새로 만드는 것과 같은 시간).
- 직접 쓴 질문, 증거 제시, 블러핑은 미리 만들 수 없어 그대로다(기준선 p50 5.4초).

## 적중률 정의 변경 (PRD F.15, D-60)
- 옛 정의 "쓴 답 ÷ 만든 답"은 구조상 0.5를 넘을 수 없다. 한 번에 칩 2개를 만들어도 하나를 누르면 상태가 바뀌어 나머지는 쓸 수 없기 때문이다.
  기준이 0.5라 20번 준비하면 늘 자동으로 꺼졌다(이번 측정에서도 정확히 50%).
- 새 정의: 적중률 = 미리 만든 답을 하나라도 쓴 준비 ÷ 준비. 버린 비율(쓰지 않은 답 ÷ 만든 답)은 비용 지표로 따로 남긴다.
- 이번 측정의 적중률 100%는 스크립트가 늘 칩을 눌러서다. 실제 적중률은 실제 플레이 기록으로 다시 재야 한다.

## 검색 미리 하기: 보류
- 기준선에서 검색은 질문당 0.0초(10회 모두)였다. 미리 해도 줄어드는 시간이 없어 구현하지 않았다.
- 설정을 `prefetch_retrieval_on_enter: false`로 바꾸고 이유를 적었다. 외부 임베딩 모델로 바꾸면 다시 잰다.

## 한계
- 표본이 적다(방식마다 2~4번). 한 시점, 한 질문으로 쟀다.
- 버린 비율: 칩 2개를 만들면 최소 50%는 버린다. 사용량(비용)이 그만큼 는다.
- 개발용 명령줄 방식에서는 버린 호출을 취소해도 이미 켠 프로그램은 끝까지 돈다(결과만 버림). API 방식이면 요청이 끊긴다.
- 화면 연결(심문 시작·행동 끝에 `/prepare` 호출)은 화면 테스트·빌드로만 확인했다. 실제 플레이에서 적중률과 체감을 봐야 한다.
