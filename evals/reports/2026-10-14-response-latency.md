# 응답 지연 기준선 (2026-10-14)

## 목적
심문 중 질문을 보내고 답이 나오기까지 왜 느린지 원인을 나눠 본다.
PRD §17.1 목표는 질문→답 p50 3초, p95 6초 이하다.

## 환경
- 개발 PC(Windows 11). 서버 `uvicorn`, 화면은 Vite 개발 서버.
- 글 모델 연결: 개발용 프로필 `dev` = 로그인된 AI 명령줄 도구를 질문마다 실행(`server/llm/cli_provider.py`).
  - 실제 도구·모델 이름은 커밋하지 않는 `config/models.local.yaml`에만 있다. 아래 실험은 모두 같은 모델이다.
- 비교용 프로필 `api` = 같은 모델을 OpenAI 호환 API 주소로 호출(`server/llm/client.py`, 커밋 480042f).
  - 사용자 결정(2026-10-14)으로 지금은 쓰지 않는다. 비교 실험에만 썼다.
- 지연 시간은 `Tracer`가 남긴 호출 단위 벽시계 시간이다(명령줄 방식은 프로그램 시동·종료 포함).

## 다시 돌리는 법
측정 도구 `server/llm/latency.py`(테스트 `tests/core/test_latency.py`).

```
# 1번 표: 기록 요약 (모델을 부르지 않음)
uv run python -m server.llm.latency --since "2026-10-14 13:40" --until "2026-10-14 13:59"
# 3번 실험처럼 기록된 요청을 지금 설정으로 다시 보내기 (진짜 모델 사용량이 든다)
uv run python -m server.llm.latency --since "2026-10-14 13:40" --until "2026-10-14 13:59" --replay 4 --roles npc
```

- 2번과 3번 실험(시동 시간, 생각 끔, 미리 켜 두기, API 비교)은 이 도구가 생기기 전에 임시 스크립트로 쟀다.
  앞으로의 비교는 이 도구로만 한다.

## 1. 실제 플레이 기록 (기준선)
- 근거: `var/traces.jsonl`, 2026-10-14 13:42~13:57 한 판(기본 사건), 질문 10개.
- 질문 1개 = (LLM 라우터가 돌았으면 그 시간) + 검색 + NPC 답. 검색은 매번 0.0초.

| 값 | 질문→답 (초) |
|:--|:--|
| 10개 정렬 | 3.7, 4.1, 4.2, 4.3, 5.4, 5.6, 7.3, 8.1, 8.3, 14.3 |
| p50 | 5.4 (가까운 순위 방식) |
| 최대 | 14.3 (LLM 라우터 9.1 + NPC 5.2) |

- 목표 대비: p50 5.4초(목표 3초), 6초를 넘은 질문 4/10.
- LLM 라우터는 10개 중 1번 돌았다(시맨틱 분류가 애매할 때만 도는 설계, PRD §7.1).

## 2. 명령줄 도구의 시동 시간
- 방법: 한 단어로만 답하는 짧은 요청을 같은 옵션으로 2번 실행. 전체 벽시계 시간과 도구가 보고한 모델 시간을 비교.

| 회차 | 전체 | 모델 | 차이(시동·종료) |
|:--|:--|:--|:--|
| 1 | 5.0초 | 1.5초 | 3.5초 |
| 2 | 4.0초 | 2.1초 | 1.9초 |

- 해석: 질문마다 약 2~3.5초가 모델과 상관없이 프로그램을 켜고 끄는 데 쓰인다. API 방식에는 없는 시간이다.

## 3. 같은 질문을 다시 보내기 (재현 실험)
- 방법: 1번 기록의 NPC 요청 중 최근 4개(긴 답 2개, 짧은 답 2개)의 지시문·질문을 그대로 다시 보낸다. 한 번에 하나씩 보낸다.
- "생각"은 모델이 답하기 전에 하는 추론이다. 화면에 보이지 않지만 출력 토큰과 시간에 들어간다.

### 3-1. 명령줄 도구 (긴 답 1개, 짧은 답 1개)
| 조건 | 긴 답 | 짧은 답 | 긴 답 출력 토큰 |
|:--|:--|:--|:--|
| 지금 설정 | 9.9초 | 7.0초 | 796 |
| 생각 끔 (도구의 생각 토큰 상한을 0으로) | 5.5초 | 4.5초 | 329 |
| 생각 끔 + 미리 켜 둔 프로그램에 질문만 전달 | 3.5초 | 2.3초 | 308 |

- 미리 켜 두기: 실시간 입력 형식으로 프로그램을 먼저 켜 두면 90초 동안 질문을 기다렸다(메모리 약 180MB). 90초 뒤 짧은 질문의 답이 1.6초 만에 나왔다.

### 3-2. API (같은 4개 요청)
| 조건 | 결과 (초) | 출력 토큰 |
|:--|:--|:--|
| 기본(생각 켜짐) | 7.9, 9.1, 2.1, 3.3 | 702, 647, 123, 115 |
| 생각 끔, 3회 반복(12번) | 중앙값 약 2.2, 범위 1.7~5.2, 한 번 11.0 | 99~264 |

- 해석: API로 바꿔도 생각이 켜져 있으면 긴 답은 8~9초로 그대로다. 긴 답을 늦게 만드는 주원인은 생각 토큰이다.

## 결론
질문→답이 느린 원인은 세 가지다.
1. 개발용 명령줄 도구를 질문마다 켜고 끄는 시간(2~3.5초). 개발 PC에만 있다.
2. 생각 토큰. 긴 답에서 출력이 2~3배로 늘어 4~5초가 더 든다. 공급자와 상관없다.
3. 애매한 질문에서 도는 LLM 라우터(+9초, 10개 중 1번).

## 결정 (사용자, 2026-10-14)
- 지금은 API 키를 쓰지 않는다. 개발은 명령줄 도구로 계속한다.
- 개발 PC에서만 빨라지는 꼼수(프로그램 미리 켜 두기 등)는 하지 않는다. 출시 때 API로 바꾸면 버려지기 때문이다.
- 개발 PC와 출시 환경 어디서든 똑같이 효과가 나는 공통 경로만 고친다(PRD §14.1).

## 한계
- 표본이 적다(실제 질문 10개, 재현 4개). 한 시점, 한 네트워크에서 쟀다.
- 생각을 끈 답의 품질(말투, 거짓말 유지, 근거)은 아직 평가하지 않았다. 속도와 함께 확인해야 한다.
- 화면 쪽 시간(이벤트 전달, 글자 흘리기 연출)은 빠져 있다.
