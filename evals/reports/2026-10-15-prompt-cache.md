# 프롬프트 앞부분 고정 (2026-10-15)

응답 속도 개선 3단계. 기준선은 [2026-10-14 응답 지연 기준선](2026-10-14-response-latency.md).

## 목적
인물 답 지시문 안에 행동마다 바뀌는 값(게임 속 날짜·시각·장소)이 들어 있어 프롬프트 캐시가 매번 깨지는지 확인하고 고친다.
PRD §12.8 캐싱 규칙("시각처럼 매번 바뀌는 값을 앞부분에 넣지 않는다")과 코드가 어긋나 있었다.

## 바꾼 것
- 전: 지시문 = 공통 규칙 + 인물 설정 + `[사건 공통 정보] 수사 1일차 15:00, 장소: 3층 개발팀 사무실. 사건: …` (+ 출력 형식 안내)
- 후: 지시문 = 공통 규칙 + 인물 설정 + `[사건 공통 정보] 사건: …` (+ 출력 형식 안내). 한 판 동안 인물마다 그대로다.
  사용자 글 맨 앞에 `[지금] 수사 1일차 15:00, 장소: …`를 둔다(`server/agents/npc.py` `build_prompt`, `NPCContext.scene`).
- 심문 답, 증거 제시·블러핑 반응 모두 같은 경로다.

## 방법
지난 판 기록의 인물 답 요청 1개를 시각만 1시간 바꿔 두 번 보내고, 두 번째 호출의 캐시 칸(usage)을 본다.
개발용 모델 연결(명령줄 도구)이 돌려주는 `cache_read_input_tokens`·`cache_creation_input_tokens`를 썼다.
- 측정 스크립트는 임시로 썼다(저장소 밖). 같은 측정을 지연 측정 도구에 넣는 것은 다음 할 일로 남긴다.

## 결과
| | 두 번째 호출(시각만 바뀜)에서 캐시로 읽은 토큰 | 새로 처리한 토큰 |
|:--|--:|--:|
| 전 (시각이 지시문 안) | 589 | 1,999 |
| 후 (시각이 사용자 글 앞) | 1,547 | 1,045 |

- 시각이 바뀌어도 캐시에서 바로 읽는 앞부분이 2.6배가 됐다. 남은 1,045토큰은 기억·질문이라 원래 질문마다 바뀐다.
- 같은 요청을 그대로 다시 보내면 2,588토큰 전부 캐시에서 읽었다(캐시 자체는 동작함).
- 참고: "전" 상태를 같은 시각에 다시 재려 했으나 앞선 측정의 캐시가 남아 있어 두 호출 모두 2,588을 읽었다. 그래서 비교에는 첫 측정값을 쓴다.

## 해석
- 캐시로 읽는 입력은 공급자 대부분에서 값이 싸고(보통 일반 입력의 10% 안팎), 첫 글자까지의 시간도 조금 준다.
  이번 표본(호출 몇 번)으로는 시간 차이를 말할 수 없다. 모델 시간은 2.2~4.5초로 흔들렸다.
- 출시용 API 연결(OpenRouter)에서도 앞부분이 같아야 캐시가 붙는 것은 같다. 그래서 이 수정은 개발·출시 공통 경로다.

## 한계
- 호출 2쌍만 쟀다. 캐시 유지 시간(보통 5분~1시간)이 지나면 첫 호출은 다시 새로 처리한다.
- 지시문이 짧은 역할(라우터·게임 마스터 검사)은 손대지 않았다.

## 다음
- 지연 측정 도구가 호출 기록의 캐시 토큰도 모아 캐시 적중률(PRD §17.1)을 내게 한다.
- 4단계: 역할별 생각(추론) 깊이를 공급자와 상관없이 설정으로 정한다.
